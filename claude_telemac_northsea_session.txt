● The TELEMAC-2D version of the North Sea example is set up in telemac_northsea/
  and runs end to end. The one real difference from thetis is the time step:
  TELEMAC is unstable at thetis's dt = 3600 s, so it uses 300 s. Mesh, forcing
  and gauge outputs match thetis.

  The simulated gauge levels match observations well
  (north_sea_elev_ts_telemac.png). I couldn't compare against thetis itself,
  because there's no thetis outputs/ from run.py, and outputs_spinup stops after
  1 day.

  Workflow
  python prepare_telemac.py                       # needs firedrake + thetis
  source ~/prj/telemac/setenv_telemac.sh
  telemac2d.py t2d_spinup.cas                     # 2022-01-01 → 01-15, ramped 
  forcing
  telemac2d.py t2d_run.cas                        # 2022-01-15 → 01-18, restarts
  from the spinup
  python postprocess.py --plot                    # gauge output → thetis-style 
  hdf5 + plot
  Each run takes well under a minute.

  What matches thetis
  - Mesh and bathymetry: taken from north_sea_bathymetry.h5 (6396 nodes, P1
    bathymetry). I didn't use north_sea.msh, which is a different mesh (6565
    nodes).
  - Physics: Manning n = 0.03, no viscosity, no wetting and drying.
  - Coriolis: f = 2Ω sin(lat), computed per node with thetis's coordinate
    system. TELEMAC only offers a constant Coriolis value in Cartesian
    coordinates, so user_fortran/prosou.f overrides it to read f from the
    geometry file.
  - Tidal forcing: the boundary elevations come from thetis's own
    TPXOTidalBoundaryForcing, with the same 8 constituents, start dates and
    14-day linear ramp. They're written every 300 s at each open-boundary node,
    so TELEMAC gets the same values thetis does, not its own TPXO interpolation.
  - Gauges: the same 8 locations from stations_elev.csv, output daily in the
    spinup and hourly in the run, as in thetis. postprocess.py writes them as
    diagnostic_timeseries_<sta>_elev.hdf5 in thetis's format.

  Choices for you
  1. Time step (the main difference). TELEMAC's finite-element solver treats
     Coriolis explicitly, and with f·dt ≈ 0.44 it blows up within a few days. I
     tested:

  | dt                      | Result
              |
  |-------------------------|---------------------------------------------------
  -------------|
  | 3600 s without Coriolis | stable
              |
  | 3600 s with θ = 1       | still blows up
              |
  | 1200 s and 1800 s       | go unstable over the 14-day spinup
              |
  | 600 s                   | stable, but ~0.25 m rms off dt = 150 s at the
  North Sea gauges |
  | 300 s                   | within ~3 cm of dt = 150 s everywhere except Maloy
  (~0.2 m)    |
     I chose 300 s. Getting dt = 3600 s to work would mean making Coriolis
     implicit inside TELEMAC's wave-equation solver, which changes its core
     numerics. I didn't attempt that; say if you want me to.
  2. Discretisation. Thetis uses DG-P1 with the DIRK22 time stepper. TELEMAC
     uses its standard P1-P1 wave-equation scheme with θ = 0.55, characteristics
     for advection and a CG solver at 1e-8. These are inherently different.
  3. Open boundary. Thetis imposes elevation weakly with an external velocity
     of 0. In TELEMAC the elevation is strongly imposed and the velocity is left
     free (code 5 4 4). The two nodes where the open boundary meets the coast
     are set as solid.
  4. Restart. The run restarts from TELEMAC's own day-14 spinup state, just as
     thetis restarts from its own.

  Environment notes
  - The ~/fdm venv can't import firedrake: the firedrake checkout is newer than
    the installed fenics-ufl. I used ~/fdr (its own thetis checkout,
    2026.8.dev4) for preprocessing and plotting, and didn't change either
    environment.
  - In the run file I removed COMPUTATION CONTINUED, which v9 dropped; PREVIOUS 
    COMPUTATION FILE alone triggers the restart.
  - I set MAXIMUM NUMBER OF BOUNDARIES = 3000: TELEMAC sizes its arrays for
    per-node boundary data from that keyword, and we have 2279 boundary nodes.
